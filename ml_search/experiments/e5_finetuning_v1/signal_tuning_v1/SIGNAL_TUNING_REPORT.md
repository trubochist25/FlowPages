# Настройка взаимодействия сигналов

## Решение

Рабочие веса полного поиска оставлены без изменений:

| Сценарий | Семантика | Текст | Предпочтения | Популярность | Рейтинг |
|---|---:|---:|---:|---:|---:|
| Обычный содержательный запрос | 0,70 | 0,25 | — | 0,03 | 0,02 |
| Запрос с распознанными предпочтениями | 0,70 | 0,23 | 0,02 | 0,03 | 0,02 |

Правила для распознанных названий и авторов не менялись. Они используют
отдельные минимальные оценки и защищают навигационные запросы от сдвига шкалы
эмбеддингов.

## Перебор весов

Проверено 45 вариантов, удовлетворивших ограничению по 77 регрессионным
запросам. Выбор выполнялся по семейному NDCG@10 на 51-запросной настроечной
выборке. Новые 99 тестовых запросов не открывались.

Максимальный NDCG дал вариант с весом семантики 0,85 для обычных запросов и
0,80 для запросов с предпочтениями. Он повысил NDCG с 0,2362 до 0,2534 и
Hit@10 с 43,59% до 51,28%, но снизил Hit@3 с 25,64% до 23,08% и потерял один
регрессионный запрос в топ-10.

Вариант, сохраняющий Hit@3 настроечной выборки, получил NDCG 0,2527 и тот же
Hit@10 51,28%, но также потерял один регрессионный запрос. Таким образом,
повышение веса семантики меняет полноту на точность первых позиций, а не даёт
однозначное улучшение.

При leave-one-family-out проверке веса каждый раз выбирались без одного целого
семейства. Средний NDCG автоматически выбранных весов составил 0,2325 против
0,2362 у текущих весов. Разница −0,0037 показывает, что выигрыш общего перебора
не переносится на исключённые семейства. Поэтому новые веса не подключены.

## Запросы без соответствия

Одиночный порог косинусной близости оказался непригоден: порог, находящий все
пустые запросы, сохранял только 20,5% запросов с подходящими книгами.

Дополнительно проверен классификатор по десяти признакам: абсолютная семантика,
её нормированная высота и разрывы, текстовое совпадение, итоговая оценка,
согласие семантической и текстовой выдачи, доля известных слов. Проверка
выполнялась с исключением целых семейств. Классификатор сохранил 71,8%
содержательных запросов и распознал только 41,7% пустых; сбалансированная
точность — 56,7%. Он также не подключён.

## Поведение пустой выдачи

Поиск различает два доказуемых состояния:

- `no_matches` — после строгих фильтров в каталоге объективно не осталось ни
  одной книги;
- `invalid_query` — запрос не содержит слова или числа.

Для свободного текстового запроса низкая оценка означает только неуверенность
модели. Она не доказывает, что подходящей книги в каталоге нет. Пока нет
надёжного классификатора абсолютной релевантности, API возвращает ближайшие
книги со состоянием `results` или `partial` и не объявляет каталог пустым.
Такое поведение может давать слабые рекомендации, но не скрывает потенциально
подходящие книги ложной пустой выдачей.

Для настоящего автоматического отказа нужен отдельный pointwise/cross-encoder
классификатор «запрос — книга подходит / не подходит». Его следует обучать на
проверенных парах и большем числе независимых пустых семейств. Повторное
дообучение E5 для этой задачи сейчас не обосновано: проблема относится к
абсолютной оценке соответствия, тогда как E5 обучена относительному
ранжированию.
